# Таро-приложение: техническое исследование
Составлено: 2026-10-14. Только исследование, кода нет.

## 1. Архитектура: варианты «оболочки»

### (a) Встраиваемый виджет через iframe
Классика: на сайте вставляется `<iframe src="https://tarot.example.com/embed/spread/3cards">`.
- Плюсы: встраивается в любой сайт одной строкой; стили и JS виджета полностью изолированы от стилей сайта-хозяина (не будет конфликтов CSS); разработка — обычное веб-приложение; легко версионировать (обновил сервер — обновилось везде).
- Минусы: некоторые сайты режут iframe политикой безопасности; куки внутри iframe считаются third-party — Safari/Firefox могут блокировать сессии (лечится: авторизация через токен в URL или postMessage-мост, либо SameSite=None; Secure); автовысоту iframe приходится синхронизировать через postMessage; в Telegram Mini App не нужен.
- Для «блоков-раскладов» удобно: каждый расклад — отдельный URL (`/embed/daily`, `/embed/celtic-cross`), сайт-хозяин выбирает нужный.

### (b) Виджет через script-тег
Сайт подключает `<script src=".../widget.js">`, скрипт рендерит расклад прямо в DOM страницы.
- Плюсы: выглядит «родным», наследует шрифты/тему сайта, нет проблем с высотой.
- Минусы: CSS виджета может конфликтовать со стилями сайта (лечится Shadow DOM, но это усложняет); JS в одном контексте — выше риск поломок от чужого кода; сложнее с авторизацией.
- Вывод: для MVP хуже iframe — больше краевых случаев при встраивании в чужие сайты.

### (c) Telegram Mini App
Обычное веб-приложение, которое открывается внутри Telegram по ссылке из бота (WebView). Telegram сам передаёт подписанные данные пользователя (initData) — авторизация получается «бесплатно», без логина/пароля. Аудитория уже сидит в Telegram, пуши — нативные.
- Плюсы: ноль трения при входе; тот же код, что и сайт; можно открывать кнопкой из бота (`t.me/bot/appname`).
- Минусы: работает только внутри Telegram (для встраивания в обычный сайт не подходит); WebView капризнее обычного браузера (особенности viewport на iOS, safe-area); для платежей/уведомлений свои API.

### (d) PWA (прогрессивное веб-приложение)
Тот же сайт + манифест и service worker: «установка» на телефон, офлайн, свои пуш-уведомления.
- Для MVP — необязательно; добавляется позже поверх варианта (a).

### Рекомендация
**Основой делать одно веб-приложение (вариант a), которое одновременно:**
1. встраивается в любой сайт через **iframe** (`/embed/...` — по одному URL на расклад/блок);
2. открывается как **Telegram Mini App** по кнопке из бота (тот же код, другой entry-point с initData-авторизацией).

Один код — три поверхности: сайт, чужой сайт (iframe), Telegram. Это стандартный приём: Mini App технически и есть обычная веб-страница, загружаемая с URL разработчика. Отдельный script-виджет не делать — iframe покрывает встраивание проще и надёжнее.

## 2. Telegram Bot API: привязка аккаунта, рассылки, лимиты

### Привязка «сайт ↔ Telegram» через одноразовый код (как в Help)
Проверенный паттерн, два направления:
- **Сайт → бот (удобнее):** залогиненный пользователь на сайте жмёт «Привязать Telegram» → сервер генерирует короткий код (8–10 символов, TTL 10 минут, одноразовый, хранится только хэш) → пользователь отправляет боту `/link КОД` → бот сверяет код с сервером и сохраняет `telegram_id` в профиль. Сайт опрашивает статус привязки и показывает «Привязано ✓».
- **Бот → сайт:** пользователь пишет боту `/start` → бот выдаёт код → пользователь вводит его в личном кабинете на сайте. Работает даже если на сайте ещё нет аккаунта (код можно использовать как инвайт для регистрации).
- Код одноразовый, сгорает после использования; повторная привязка — через `/unlink` + новый код. Ограничить частоту генерации кодов (анти-спам).

### Deep linking
Ссылка `t.me/имя_бота?start=ПАРАМЕТР` открывает чат с ботом и передаёт параметр в обработчик `/start`. Ограничения: параметр до 64 символов, только `A–Z a–z 0–9 _ -`. Применение: кнопки «Открыть расклад в боте», персональные инвайт-ссылки, возврат из Mini App. Для запуска Mini App с параметром — `t.me/имя_бота/имя_приложения?startapp=параметр`.

### Лимиты отправки (актуально на 2026)
- ~30 сообщений/сек на все чаты суммарно (массовые рассылки);
- ~1 сообщение/сек в один конкретный чат (короткие всплески терпимы);
- ~20 сообщений/минуту в одну группу;
- при превышении — HTTP 429 с полем `retry_after` (секунды). Правило: ждать ровно `retry_after` и только потом повторять, иначе бан растягивается. Для MVP с сотнями пользователей лимиты не страшны, но очередь отправки с бэкоффом заложить сразу.
- Сообщение — до 4096 символов; фото карты дня лучше слать как `sendPhoto` с подписью (caption тоже до 1024 символов) — картинка повышает открываемость.

### Подводные камни
- Бот не может написать пользователю первым, пока тот не нажмёт /start (иначе 403). Поэтому «карта дня» работает только для привязанных пользователей, которые стартовали бота.
- Webhook требует HTTPS (порты 443/80/88/8443); для MVP проще long polling — не нужен белый IP и домен с TLS, бот сам опрашивает Telegram. На масштаб переходить на webhook.
- Токен бота — только в переменных окружения, никогда в коде/репозитории. В логах маскировать.

## 3. Авторизация для MVP

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Логин + пароль** (как в Help) | Привычно; работает везде, включая iframe; полный контроль | Нужно хранить хэши (bcrypt/argon2), восстановление пароля, защита от перебора |
| **Telegram Login Widget** | Вход в один клик для пользователей Telegram; без паролей; подпись проверяется HMAC по токену бота, `auth_date` не старше суток | Только для владельцев Telegram; виджет — внешний скрипт с telegram.org |
| **Mini App (initData)** | Внутри Telegram авторизация вообще не нужна — Telegram сам присылает подписанные данные пользователя; сервер проверяет HMAC-SHA256 и выдаёт свою сессию/JWT | Работает только внутри Telegram |
| **Парольлесс (код на e-mail)** | Без паролей; проще безопасно | Нужен почтовый сервис; лишний шаг каждый вход |

### Рекомендация
**Логин+пароль как основной** (как в Help — пользователю привычно, работает в iframe), **плюс** вход через Telegram Login Widget как альтернатива и **автовход через initData** внутри Mini App. Привязка бота — одноразовым кодом в обе стороны (раздел 2). На старте: регистрация по логину/паролю → кнопка «привязать Telegram» → дальше карта дня падает в бот.

## 4. Стек для одного специалиста (прагматичный)

**Фронтенд:** vanilla HTML/CSS/JS без сборщика. Обоснование: виджет-расклад — это в сущности интерактивная страница (вытянуть карту, показать толкование); фреймворк (React/Vue) даст мало, а сборка и зависимости добавят хрупкости. Один и тот же код обслуживает сайт, iframe-embed и Mini App. Стили — CSS custom properties, чтобы сайт-хозяин мог перекрашивать виджет под себя через параметры (`?theme=dark&accent=gold`).

**Бэкенд:** Python — **FastAPI** (API + страницы) + **aiogram 3.x** (бот, нативный asyncio, активное русскоязычное сообщество, стандарт де-факто для новых проектов в 2026). Оба — один язык, один деплой. Альтернатива — Node + grammY, если специалист сильнее в JS; функционально равноценно.

**База данных:** на MVP — **SQLite** (нулевое администрирование, файл рядом с приложением), схема сразу совместимая с Postgres; при росте — переезд на Postgres одной миграцией. Таблицы: users, telegram_bindings (коды привязки), spreads (история раскладов пользователя), daily_queue (очередь карты дня), notification_prefs.

**Контент (карты, толкования, расклады):** **JSON-файлы в репозитории**, а не в БД. Почему: толкования — это тексты, их удобно править, ревьюить и версионировать в git; структура данных простая и редко меняется схемой. В БД — только пользовательский контент (его расклады, избранное). Формат: `decks/cosmic-mysticism/cards.json` (название, файл картинки, прямое/перевёрнутое значение, ключевые слова), `spreads/*.json` (название, число позиций, схема раскладки, описание каждой позиции).

**Картинки карт:** статика на том же сервере (`/static/decks/...`) или CDN; для бота — `sendPhoto` по URL или file_id (после первой отправки Telegram возвращает file_id — дальше отправка без повторной загрузки).

**Хостинг:** VPS (уже есть опыт с Help) + Docker Compose: контейнеры `web` (FastAPI), `bot` (aiogram, long polling на MVP), `scheduler` (APScheduler/скрипт по cron). Альтернативы без своего администрирования сервера: Railway / Fly.io / Render. Домен + HTTPS обязателен только для webhook и Login Widget (для polling MVP можно без).

## 5. Ежедневная «карта дня» в Telegram: как обычно реализуется

1. **Хранение настроек:** у пользователя `timezone` (IANA, например `Europe/Moscow` — берётся из браузера при регистрации, можно менять в профиле), `daily_time` (например `08:00`), флаг подписки.
2. **Планировщик:** тикающий каждые 5–15 минут джоб (APScheduler внутри процесса, systemd timer или cron). Каждый тик: `SELECT users WHERE subscribed AND local_time(now, timezone) >= daily_time AND NOT sent_today`. 
3. **Защита от дублей:** таблица-реестр отправок `(user_id, date)` с уникальным ключом — повторный прогон никого не заспамит.
4. **Очередь отправки:** отправка идёт через очередь с лимитером (не чаще ~25 msg/sec глобально, пауза по `retry_after` при 429). На MVP хватит последовательного цикла с небольшой задержкой; очередь (Redis/Bull/pgmq) — при тысячах пользователей.
5. **Контент карты дня:** случайная карта из колоды (seed = user_id + date, чтобы «перевытянуть» было нельзя читом), картинка + короткое толкование «что ждёт сегодня» + кнопка «Открыть полный расклад» (deep link в Mini App/сайт).
6. **Часовые пояса:** никогда не хранить «время отправки в UTC» как константу — пересчитывать каждый тик по таймзоне пользователя; аккуратнее с переходом на летнее/зимнее время (IANA-зоны это учитывают сами).
7. **Отписка:** команда `/stop` в боте и тумблер на сайте; обработка 403 (пользователь заблокировал бота) — помечать подписку неактивной, а не ронять джоб.

## 6. Модульность «оболочки» (блоки)

- Каждый расклад — плагин: JSON-описание (позиции, схема) + JS-модуль рендера. Ядро (перетасовка, анимация вытягивания, история) общее.
- Каждая колода — папка: картинки + `cards.json` с толкованиями. Новая колода = новая папка, без правок кода.
- Позже другие системы (руны, Ленорман) — тот же интерфейс плагина: «набор сущностей + расклады».
- Embed-URL вида `/embed/{deck}/{spread}` позволяет сайту-хозяину вставлять любой блок точечно.

## Итоговая рекомендация

**Делать одно веб-приложение на vanilla JS + Python (FastAPI + aiogram 3.x), SQLite на старте:**
- сайт (логин/пароль как в Help + Telegram Login Widget) → встраивание в чужие сайты через **iframe** (`/embed/...`) → тот же код как **Telegram Mini App**;
- привязка бота одноразовым кодом в обе стороны (`/link КОД`);
- «карта дня» — планировщик с тиком 5–15 минут, учётом таймзоны пользователя, реестром отправок против дублей и уважением к 429;
- контент (колоды, толкования, расклады) — JSON в git, картинки — статика;
- деплой — VPS + Docker Compose (web + bot polling + scheduler).

Почему так: один специалист пишет один код на одном языке, который покрывает сайт, встраивание и Telegram; нет сборщиков и тяжёлых фреймворков; архитектура повторяет уже знакомый пользователю Help (меньше нового); модульность «колода/расклад как папка+JSON» позволит потом добавлять другие эзотерические системы без переписывания ядра.

## Дополнение от 15.10.2026: как определять время и часовой пояс пользователя

**Как это сделано в Help (проверено по коду).** Когда человек заходит на сайт, браузер сам отдаёт часовой пояс устройства (`Intl.DateTimeFormat().resolvedOptions().timeZone`, `client/src/App.jsx`), сайт молча сохраняет его в базе (`/settings/timezone`) при каждом входе. Бот берёт сохранённый пояс (`getTimezone()`) и по нему считает время. Пояс хранится как название («Europe/Moscow»), поэтому переход на летнее и зимнее время считается сам, переспрашивать не нужно. Пока пояс не сохранён, действует значение по умолчанию (UTC).

**Для сайта «Таро» и бота «Уведомитель»:** делаем так же. Человек ничего не вводит, в профиле нет выбора пояса. Настраивается только время отправки карты дня в формате AM/PM.

**Для бота «Таролог» (у пользователей нет сайта).** Bot API Telegram не отдаёт боту часовой пояс пользователя (по результатам поиска и общим сведениям, точное подтверждение в официальной документации не проверялось). Обычные способы:
1. **Mini App (Web App) по кнопке в боте.** Страница внутри Telegram запускается в браузерном движке, читает пояс через `Intl` и отправляет на сервер. Человек нажимает одну кнопку и ничего не вводит. Хранить нужно название пояса, а не сдвиг, иначе переход на летнее время собьёт расчёт.
2. **Один вопрос в чате:** «Сколько у вас сейчас времени?». По ответу и времени сообщения считается сдвиг от мирового времени. Запасной вариант, если Mini App недоступен.
3. Приблизительные способы (по `language_code` или геолокации) ненадёжны, брать их как подсказку, а не как данные.

Для сайта в браузере пояс можно прочитать так же, но если часы на устройстве сбиты, определение будет неверным. Это редкий случай, отдельная настройка для него не нужна.
